## 一、为什么要有这张表

**文件名在本项目不是身份。** 这一条不是原则，是量出来的：

| 现象 | 实测 |
|---|---|
| `10mg 2周.mp4` 在游泳和悬尾各有一段 | 同名的两段：FST 9562 帧 / 382.48 s，TST 9661 帧 / 386.44 s，**sha256 不同** |
| `20mg 2周.mp4` 同上 | 同名跨范式，两段不同录像 |
| `zztest01.mp4` ≡ `正常5+抑郁1-3.mp4` | 转码目录里**同哈希异名**（一份字节两个名字） |
| 四个 CSI 输出目录 | **71 行记录只有 53 份互不相同的字节**（见 §五.1） |

现有登记有三处，各自都不够当身份用：`docs/CSI输入视频映射表.csv` 只有**源 sha256 前 16 位**、
没有转码件自己的哈希；`~/Downloads/tst_30clips/{manifest,cut_provenance}.csv` 以文件名为键；
`data/human_scores/manifests/*.csv` 以 `(trial_id, video_filename)` 为键、**没有视频哈希列**。
这张表把三处对不上的那部分一次性量齐：全量 sha256、帧数（含解码计数）、
平均帧率与基础帧率估计（**分列，用 ffprobe 原始字段名**）、`field_order`、容器时长、
逐包时间戳统计、来源哈希、t0、几何绑定、人工记录指针、用途组、证据级别。

**身份键是内容哈希（sha256）加上可核验的源/转码/裁剪派生关系。**
帧数、时长、时间戳都只作**一致性检查**——帧数相同只支持「数量一致」，
不证明逐帧内容或时间等价（重采样、裁剪、填边、可变帧率都还没验证过）。
原备忘这里写过「帧数才是身份键」，2026-09-19 撤回（返修 R112-02，理由见 §五.2）。

**这张表刻意不做的事**（与 Spec A §3 / Spec B §9 对齐）：

1. **不建第二套人工真值表。** 人工记录的拥有者是 `data/human_scores/manifests`；
   本表只写**指针**（`human_record_ref` + `human_record_status`），不复制 holds、不复制评分、
   不复制复评归属。缺的哈希列去 DP-082 入库侧补，不在这里另立一本。
2. **不产生任何数值结论。** 表里没有秒数、没有百分比、没有阈值。
3. **不进验收路径。** `csi_read_back_verified` 仍是 `False`；本表不改变任何冻结常量、
   不改 TST 的 θ_mob / ASSAY_WINDOWS / CSV 字段 / 历史数据 / 验收门。
4. **缺失的身份不写成空行假装存在**（见 §六）。

## 三、列口径与状态词表

32 列分七组（2026-09-19 返修：原 25 列）。**状态词是口径，不许当形容词用**：
写进表里的每个值都在下面有定义，新增取值必须先改这里。

> **改列名就是改口径，所以列名一律用 ffprobe 的原始字段名。** 原来那两列叫
> `fps_rational` / `fps_field_rate` —— 后者替 FFmpeg 下了一个它没下的结论
> （`r_frame_rate` 官方定义是「能表达该流时间戳的**基础帧率估计**」，不是场频）。
> 现已改名为 `fps_avg_frame_rate` / `fps_r_frame_rate`，并把解释放回文档、不放回列名。

**① 身份**：`material_id`（`<来源>:<范式>:<文件名>`，全表唯一）、`assay`（FST/TST/na）、
`role`、`path`（一律 `~/` 起，不写绝对用户路径）、`bytes`、`sha256`（全量 64 位小写）。

**② 流元数据**：`codec`、`width`、`height`、`field_order`（ffprobe 原样：本批
`progressive` 66 行、mjpeg 不上报 2 行，**没有一行是隔行**）。

**③ 帧数与帧率**：`frames`、`frames_source`、`fps_avg_frame_rate`、`fps_r_frame_rate`、
`duration_s`、`frames_vs_dur_x_avgfps`。

- `frames_source=container`：容器自己写着帧数（源片 mp4、mjpeg avi），52 行。
- `frames_source=decode_count`：容器**没有**帧数，用 `ffprobe -count_frames` 的
  `nb_read_frames` 逐帧解码数出来（MPEG-1 转码件 + 1 个 MPEG-2 中间件），16 行。
- `fps_avg_frame_rate` = ffprobe 的 `avg_frame_rate`（容器声称的平均帧率，本批全是 25/1）。
- `fps_r_frame_rate` = ffprobe 的 `r_frame_rate`（**基础帧率估计**）。15 个 MPEG-1 转码件上
  它是 50/1 而 avg 是 25/1 —— 这个**差异是实测事实**；把它读成「隔行场频」是
  **已被自己的数据撤回的解释**（见 §五.2）。
- `frames_vs_dur_x_avgfps`：`container` 行判 `|n − d·fps| ≤ 0.5`；`decode_count` 行判
  `0 ≤ n − d·fps ≤ 1.5`（**方向有意义**：帧数少于时长×帧率 = 掉帧 = 转码事故，必须红）。
  这一列**只判数量自洽**：过了不等于逐帧内容或时间等价。生成器在发布前会**重算并对表**，
  空值或与重算不符一律停机（不许有一列 quietly 变成没检查过）。

**④ 时间戳实测**：`pts_count`、`pts_na`、`pts_min_s`、`pts_max_s`、`pts_spacing_uniform`、
`pts_raw_order_monotonic`。逐包 `pts_time` 的统计，**排序后**判间隔——源片 h264 的包序是
解码序（有 B 帧），原样读会出现负间隔，所以「包序是否单调」单独记一列：它不是错误，
它正是「包序 ≠ 展示序」的证据。详见 §五.2。

**⑤ 来源**：`derives_from_sha256` + `derives_from_status`
∈ `confirmed`（`cut_provenance.csv` 逐段记了源全量哈希，27 行切片）/
`confirmed_by_mapping_table`（仓库映射表点名，14 行转码件）/
`unknown_provenance`（**没有任何记录**：11 个转码中间件 + 2 个 fallback 转码件）/ `na`。

**⑥ t0**：`t0_source_s`（一律空）+ `t0_status` ∈
`not_found_in_checked_materials`（FST 视频行 27 行）/
`na_tst_no_water_entry`（TST 视频行 41 行）/ `na`（非视频行 90 行）。
**空是声明出来的，不是漏填**；而且**分范式给理由**——TST 没有「入水」这件事，
把 FST 的理由套到 TST 上就是编了一个不存在的原因。词面也限定范围：
「在本次核对的材料中未取得」≠「任何人的任何记录里都不可能有」（见 §六第 1 条）。

**⑦ 几何与人工记录**：`geometry_binding`（如 `10mg 2周.CLB`）+ `geometry_binding_status`
∈ `bound_by_filename_only`（25 行，**只按文件名挂，没有任何人工确认**）/ `na`；
`human_record_ref` + `human_record_status` ∈ `pointer_only_joins_by_filename`（15 行，
在评分员清单里被点名过，但**只能按文件名连**）/ `none_recorded`（26 行）/ `na`。

**⑧ 用途与证据**：`usage_group` ∈
`historical_or_dev_validation`（135 行，**已被研究过**：R3 全量对照、DP-053/055/059。
不得当新盲测）/ `test_golden`（6 行夹具）/ `engineering_only`（15 行：中间件、登记表）/
`forensic_hash_only_no_run_scope`（2 行 EXE，见 §四）；
`evidence_status` ∈ `artifact_checked`（150 行：实物在本机、哈希与元数据当场量过）/
`independently_reproduced`（6 行：本仓自有解析器独立复算过其内容）/
`static_recovered`（2 行：从 zip 里管道取哈希，本次未运行）。

## 四、EXE 两行是怎么处理的

**两件事必须分开写，混写就是把「这次没许可」说成「永远不可能有许可」**：

- **永久禁止**的是：把 CSI DT 加载进**自建参考器/产品**里执行（Spec B:32、SPEC:167）。
  这一条没有 scope 扩展的余地。
- **当前没有许可**的是：启动原 EXE 做动态观测、写测试副本。Spec B:36 说的是
  「现有报告的分析范围为静态/只读；启动原 EXE、动态观测、写测试副本，必须已有对应许可
  或先取得明确 scope 扩展」，Spec B:38 另说授权范围内可把原 CSI 程序当**黑盒**对照——
  那与「把 DT 加载进我们自己的代码」是两回事。逆向报告 R1 §9（:312-320）也写明：
  当轮没有运行 EXE 是因为**该案卷是离线只读的**，并建议后续在隔离的兼容 Windows VM 里
  用 demo 视频与副本输出目录做动态验证。

所以行里写的是**精确的当前许可状态**，不是一条永久裁决：
`usage_group=forensic_hash_only_no_run_scope`（只哈希；**未查到覆盖「运行原 EXE」的许可**）、
`evidence_status=static_recovered`、`path` 记成 `~/Downloads/Depressionscan  HR.zip!<内部路径>`。
本脚本只哈希，不申请也不制造任何新的动态授权。
哈希用 `unzip -p` 管道算，**不落盘、不解包整包**。两个内部路径带安装目录前缀
（`Depressionscan  HR/ForcedSwimScan-Ver2/HR-V2.0/ForcedSwimScan.exe`），裸文件名匹配不到 —— 这是实测踩过的。

两个哈希与逆向报告（`docs/逆向/2026-09-09…` §目标哈希）**逐字一致**，2026-09-18 在本机独立复算：

| EXE | sha256 |
|---|---|
| `ForcedSwimScan.exe` | `341a5ba8d9bec53455234a7872ef2bb57cff837c04efaa2ce8d6f5533e2bd054` |
| `TailSuspScan.exe` | `aa85e490abd8c605ac0ac52f874a9c1a7f679b094e6ffb8a8da346690ecbc95c` |

守卫测试把这两个值钉死（`EXE_SHA`）：取证材料被掉包，测试当场红。
**哈希一致只证明「目标身份对得上」**，不证明我们对它的字段解释是对的（返修 R114-07）。
**DT 一律不加载、不执行**（Spec B:32 / SPEC:167）；FSR3/TSR1 reader 默认不做（SPEC:166）。

## 五、量出来的三件事

### 1. 四个 CSI 输出目录**不是四次运行**（53 份字节，71 行记录）

| 目录对 | 同名同哈希文件数 |
|---|---|
| `CSI分析强迫游泳数据_对照参数`（7 个） ∩ `正常1-4对照数据`（7 个） | **6** |
| `CSI分析强迫游泳数据`（43 个） ∩ `剩余游泳视频数据`（14 个） | **12** |

- 对照参数目录多一个 `正常1-4对照更改.SET`；正常1-4对照数据目录多一个 `正常1-4对照.BMP`；
  其余 6 个文件（CLB / SET / 4 个 xlsx）**逐字节相同**。
- `剩余游泳视频数据` 的 14 个文件里 12 个与主目录同哈希，只多 2 个 BMP
  （`抑郁8-10.BMP`、`正常5+抑郁1-3.BMP`）。

**71 行 → 53 份互不相同的字节，按类型的分区是（2026-09-19 从同一份清单复算）**：

| 类型 | 行数 | **互不相同的字节** | 差额（跨目录逐字节重复） |
|---|--:|--:|--:|
| `.SET` | 5 | **3** | 2 |
| `.CLB` | 11 | **8** | 3 |
| `.xlsx` | 47 | **34** | 13 |
| `.BMP` | 8 | **8** | 0 |
| 合计 | **71** | **53** | 18 |

- 18 个差额**全部**是同扩展名、跨目录的逐字节重复，且只落在上表那两对目录里
  （12 个 fst↔rest + 6 个 ctrl↔norm14）——与「同一批交付落盘两次」的解释一致。
- **没有任何一个 sha256 同时以两种扩展名出现**，所以各类型 distinct 相加**必然**等于 53。
- 这张表**以前是手填的，填错过一次**：写成 `3 SET + 5 CLB + 43 xlsx + 4 BMP = 55`。
  55 与 distinct 总数 53 自相矛盾，而一个自相矛盾的分区在数学上就不可能正确
  ——`xlsx=43` 其实是「三个目录各自的 xlsx 行数相加」，不是全局去重数。
  现在分区由守卫测试当场从清单算（`test_csi_out_distinct_bytes_partition_is_computed_not_handwritten`），
  数字不再由人手填（返修 R114-07）。

**后果**：谁拿"我们有四个 CSI 输出目录"当"四次独立重复"，那是在数副本。
可用作对照的**互不相同**的 CSI 输出字节数上界是 **53**（xlsx 结果表 34 份）。
**统计单位要分开数**：文件数 / 副本数 / 互不相同的字节数 / 视频段数 / 动物-试次数 /
运行次数是六个不同的量，本表只钉前三个；后三个要靠人工记录才能定。

### 2. 时基：撤回两条过度结论，换成实测的四组数（返修 R112-02）

**撤回之一：「`r_frame_rate=50/1` 是隔行场频」。** FFmpeg 对 `r_frame_rate` 的定义是
「能表达该流时间戳的**基础帧率估计**」，不是场频。本轮把 `field_order` 也量了：
**68 个视频行里 66 行是 `progressive`、2 行 mjpeg 不上报，没有一行是隔行**
（`tt`/`bb`/`tb`/`bt` 一个都没有）。⇒ 50/1 **不能**读成场频；这个解释被自己的数据否掉了。
保留的**事实**是：15 个 MPEG-1 转码件上 `r_frame_rate=50/1` 与 `avg_frame_rate=25/1` 并存。
坑仍然成立——谁拿 `r_frame_rate` 当帧率，CSI 面板上的「Min Length Thresh = 15 帧」
就从 **0.6 s 变成 0.3 s**，一个看起来完全合理的数字，错一倍。但结论要写成
「用 `avg_frame_rate` + 逐包 pts」，不是「那是场频」。

**撤回之二：「帧数是身份键」。** 帧数相同**只支持数量一致**，不证明逐帧内容或时间等价；
重采样、裁剪、填边、可变帧率都**还没有验证过**，不许宣布等价。
**身份键是内容哈希（sha256）加上可核验的源/转码/裁剪派生关系**；
帧数、时长、时间戳都只作一致性检查。

**换成实测的四组数**（全部落在清单列里，每列都可复算）：

| 组 | 列 | 实测 |
|---|---|---|
| 平均帧率 | `fps_avg_frame_rate` | 68 行全为 `25/1` |
| 基础帧率估计 | `fps_r_frame_rate` | 53 行 `25/1`；15 行 `50/1`（全为 MPEG-1 转码件） |
| 帧数 | `frames` + `frames_source` | `container` 52 行 / `decode_count` 16 行；解码计数与源片帧数逐一相等 |
| 时间戳 | `pts_*` 六列 | 见下 |

时间戳这一组是本轮**新量**的，也是撤回「帧数是身份键」之后真正顶上去的证据：

1. **排序后间隔恒定**：59 行 `pts_spacing_uniform=是`（间隔恒为 0.04 s）；
   9 行 `=否`，而这 9 行**都有缺 `pts_time` 的包**（`pts_na>0`）造成空洞——
   反过来不成立（末尾缺 pts 不造成空洞，例：`FST_dep_8to10_x2.mpg` na=1 但间隔仍恒定）。
2. **包序 ≠ 展示序**：50 行 `pts_raw_order_monotonic=否`（h264 有 B 帧 ⇒ 包序是解码序，
   原样读会出现 −0.04/−0.08 的负间隔）。所以任何时间戳校验**必须先排序**，
   否则会把正常素材判成时间轴坏了。18 行单调（MPEG-1 无 B 帧、mjpeg）。
3. **源片从 0 起，转码件从 0.54 s 起**：14 个源片 `pts_min=0`；
   **15 个 MPEG-1 转码件 `pts_min` 一律 = 0.54 s**。
4. **转码件 ↔ 源片的媒体时间映射（14 件已登记转码件，逐件核对）**：
   `pts_count` 与源片帧数**逐一相等**；起点偏移**一律 +0.54 s**；
   `pts_max` 偏移 11 件是 +0.54 s、3 件是 +0.50 s —— 已查明那 3 件
   **最后一个包的 `pts_time` 是 N/A**（`FST_20mg_1w_x2.mpg`、`FST_dep_8to10_x2.mpg`、
   `TST_20mg_1w_1to3_plus_20mg_2w_1_x2.mpg`），`pts_max` 因此读早了一帧，
   **帧数并没有少，不是掉帧**。

第 4 条正是 Spec A §6.1「若存在裁剪或转码时间变化，先验证映射」要的那个映射：
**分析素材时间 = 原视频媒体时间 + 0.54 s**（本批 MPEG-1 转码件，逐件实测）。
它是「原视频媒体时间 ↔ 分析素材时间」这两个时钟之间的**实测换算**，
与「实验经过时间」（t0）无关——t0 仍然缺，见 §六第 1 条。

**容器时长系统性偏短**：12 件短 0.5 帧（0.02 s），3 件短 1.5 帧（0.06 s）。
⇒ 容器时长不能当时基，只作一致性检查（`frames_vs_dur_x_avgfps`）。

以上钉进四条守卫：`test_mpeg1_time_base_pinned`、
`test_no_stream_is_interlaced_so_r_frame_rate_is_not_a_field_rate`、
`test_pts_columns_are_real_measurements_not_blanks`、
`test_transcode_media_time_mapping_is_measured`。
**不需要为此重新分析全部视频**：本轮只是纠正了这批字段的含义与证据边界。

### 3. 复现了备忘 §6.1 的 `.SET` 差分（证据级别升到 independently_reproduced）

`docs/备忘_CSI_FST参数与格式_2026-09-10.md` §6.1 说 `10mg 2周.SET` 与 `正常1-4对照.SET`
（都 1611 B、都 n_tanks=4）逐字节只差 **15 个字节、9 个连续段**。本轮用仓库自有
`parse_set` + 独立字节差分复算，**结论一致，并给出了分解**：

- base 之后（`rel+43..49`）差 **7 个连续字节** = `struggle_esc_thresh` 0.11→0.15 与
  `float_immobile_thresh` 0.09→0.12 两个 float32 的尾数；
- 表头里差 **8 个字节** = 4 个孔位三元组的 contrast 对：(80,70)→(70,60)、(70,60)→(60,55)、
  (80,80)→(70,70)、(60,60)→(75,70)；
- 8 + 7 = **15 字节**，1 + 8 = **9 段**。其余 1596 字节全同，13 个 Motion 数一字未变。

顺带量到 `正常1-4对照更改.SET`（1527 B、n_tanks=1）与 `正常1-4对照.SET` 的差别：
Motion **idx5..idx12 共 8 个数**全变（15,15,10,20,5,10,20,5 → 18,18,15,25,8,15,25,8），
idx0..idx4 一字未变，两个阈值浮点也一字未变；另有 48 字节长度差与 4 处小整数差落在尾部（见 §六第 5 条）。

## 八、复现方法与踩过的坑

```bash
# 首次生成（目标已存在则拒绝）
/tmp/dpx311/bin/python scripts/dp133_build_input_identity.py --out docs/共用输入身份清单_v1.csv

# 更新：必须显式 --update + 旧文件的 sha256（旧版身份核对），旧版自动留快照到仓库外
OLD=$(shasum -a 256 docs/共用输入身份清单_v1.csv | cut -d' ' -f1)
/tmp/dpx311/bin/python scripts/dp133_build_input_identity.py --update --expect-sha256 "$OLD"
# 自检通过：158 行，其中视频行 68
# 写出 → docs/共用输入身份清单_v1.csv  sha256=ad15ef4a8723e058…
# 旧版快照 → ~/.cache/dp133_manifest_snapshots/共用输入身份清单_v1.prev-0893e0ef.csv

# 只扫描 + 自检，不写任何文件（改生成器后先跑这个）
/tmp/dpx311/bin/python scripts/dp133_build_input_identity.py --dry-run
```

2026-09-19 这一版全量重跑约 **26 s**（158 行：哈希 + 元数据探针 + 逐包 pts）。
输出保护：素材/证据根目录与仓库源码目录是禁止输出区（跟随软链接）；默认不覆盖；
先写临时文件 → 读回校验 → `os.replace` 发布；失败只清理本次创建的临时文件，
**绝不动旧清单与素材**。快照默认落在 `~/.cache/dp133_manifest_snapshots/`（仓库外）——
留在 `docs/` 里会变成未跟踪文件，把收工守卫弄红。

坑（都是本轮实测踩到的，写在生成器注释里，这里汇总）：

1. **不要用系统 `python3`**（3.9.6）：仓库测试基线在 3.11 上是 629 通过 0 失败，
   系统 python 会给出 52 个假红。
2. **映射表带 UTF-8 BOM**：必须 `encoding="utf-8-sig"`，否则首列名读成 `'﻿范式'`，`KeyError`。
3. **`-count_frames` 是全局选项**，必须放在 `-select_streams` **之前**；且计数落在
   **`nb_read_frames`**，`-show_entries` 里不点名它就永远读不到 —— 第一次生成时
   16 行转码件帧数全空，而自检**一声不响**（它只检查有帧数的行）。已加两道自检：
   探针跑过（有帧率）却没帧数 ⇒ 停机；视频行数 ≠ 68 ⇒ 停机。
4. **zip 内路径带安装目录前缀**，裸文件名 `unzip -p` 匹配不到，会得到空哈希 `e3b0c44…`。
5. **`pts_time` 是解码序，不是展示序**：h264 有 B 帧，原样读出来会出现 −0.04/−0.08 的
   负间隔。任何「间隔是否恒定」的判断**必须先排序**，否则会把正常素材判成时间轴坏了。
   本轮实测：50/68 行包序不单调。
6. **`--dry-run` 不能被「目标已存在」挡住**：dry-run 的用途正是「不写任何文件地验一遍」，
   第一版把它和覆盖保护绑在一起，结果改完生成器没法自检。已分开：dry-run 只跳过
   覆盖/表头两条，**禁止输出区那条照样查**（路径合不合法与写不写无关）。
7. **建字典时键要带 assay**：只按文件名建 `源片名 → 时长` 的字典，TST 的 `10mg 2周.mp4`
   会盖掉 FST 的同名文件，于是 0.02 s 的半帧截断被读成 3.98 s 的差。守卫测试自己先犯了这个错，
   被同一批实测抓出来（已改成 `(assay, 文件名)` 复合键）。
