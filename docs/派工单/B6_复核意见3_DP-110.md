## §1 必须改

### C0（最重）把声明里的「研究版」改成「正式版」，482 条测试一条都不红

变异 N4：`DECLARATION_TEMPLATE` 里

```
本报告由 DEPRESSION-PLEX **研究版**生成。本软件当前**没有计量资质**，
                    ↓
本报告由 DEPRESSION-PLEX **正式版**生成。本软件当前**没有计量资质**，
```

**零条测试变红。**

这一轮所有围着声明的守卫，守的都是「三处同源」和「数字来自 JSON」，**没有一条守着这段话本身说了什么**：

- `test_declaration_same_source_in_all_three_outputs` 比的是 xlsx / zip 与 `report.declaration` 一致——改模板，三处一起变，「同源」照样成立。
- `test_declaration_numbers_from_json_not_hardcoded` 只管数字占位符。
- `test_validation_readings_match_documents` 管的是读数，不管散文。
- `test_declaration_template_has_no_hardcoded_numbers` 管的是「模板里不许有数字」，正好把**字**排除在外。

于是：**这个产品唯一的合规边界是一段完全没有守卫的散文。** 「研究版」→「正式版」、「不得作为计量结果」→「可作为计量结果」、整段「为什么是研究版」删掉——都能静默进主干、进安装包、进客户手里的报告。

还有一件连着的：`render_declaration(g7_threshold, g8_threshold_s, theta_mob)` **没有 mode 参数**，模板里「研究版」是写死的。而 `context_rows` 里 `add("发布态", calib_mode)` 印的是 `Mode.value`。也就是说计量版一旦出现，同一份报告里会同时出现「发布态：validated」和「本报告由 DEPRESSION-PLEX **研究版**生成…没有计量资质」——**同一份文件里两句互相矛盾的合规陈述，而且没有任何守卫会说话。**

**裁决：**

1. 新增一条守卫 `test_declaration_key_phrases_are_pinned`：把声明里**不许变的那几句**逐字钉住，作为一个模块级常量列表（放在测试文件里，不放在产品代码里，避免变成第二个真值），至少包含：
   - `研究版`
   - `没有计量资质`
   - `不得**作为计量结果`（按模板实际写法逐字抄）
   - `逐秒时间对齐门`、`未定`
   - `单个试次的秒数不要单独作为结论依据`
   - `分母不看，秒数没有意义`
   - `没有产出数字的隔间会在表里占一行并写明原因`

   断言每一句都逐字出现在 `report.declaration` 里。**改一个字就红。** 要改声明，就得同时改测试——那一下是有意的，会被 review 看到。
2. `render_declaration` 加 `mode: str` 参数；模板里的「研究版」改成占位符，由 mode 映射（`research → 研究版`、`validated → 计量版`），映射表只此一处。
3. 再加一条守卫：`report.declaration` 里出现的发布态词，必须与 `context_rows` 里「发布态」那一行**指同一个东西**（两者都由 `calib_mode` 派生，断言 research 时声明含「研究版」、validated 时不含「研究版」）。
4. 计量版的声明文案我还没写、也不该由你现在编。**mode == "validated" 时先抛 `NotImplementedError("计量版声明文案未定，M3 前不许生成计量版报告")`**，并配一条守卫。**未知不许长成一句话的样子**——尤其不许长成一句关于计量资质的话。

改完拿 N4 再打一遍（「研究版」→「正式版」），把红名贴出来。

### C1（最重）PDF 在 CI 里一次都没有真渲染过，而 ubuntu 上的「跳过」是绿的

`desktop-selftest.yml` 新增的 export smoke 步骤：

```python
try:
    render_pdf(report, pdf_path)
except FontUnavailableError as e:
    print(f'WARNING: PDF 字体不可用（CI 字体库），跳过 PDF 断言: {e}')
else:
    assert pdf_path.exists() and pdf_path.stat().st_size > 0, 'PDF 为空'
    assert header == b'%PDF', ...
```

拉 run `34812238935` 的日志，两个 job 的实际走向：

| job | 实际发生 | 步骤结论 |
|---|---|---|
| **ubuntu-latest** | `xlsx OK: 8634 bytes` → `WARNING: PDF 字体不可用（CI 字体库），跳过 PDF 断言` → `Export render smoke test PASSED` | **绿** |
| **windows-latest** | `xlsx OK: 8634 bytes` → `FontUnavailableError` → 打印这条 WARNING 时 `UnicodeEncodeError: 'charmap' codec` 炸掉 | **红** |

也就是说：

1. **ubuntu 上 PDF 根本没渲染，步骤是绿的。** 而且这不是偶发——ubuntu job 的 apt 只装了 `libegl1 libxkbcommon0 libdbus-1-3`，**没有装任何中文字体**，所以每一次都会走 `except`，每一次都绿。**这一条 smoke 是装饰。**
2. **windows 上是红的，但红的理由不是「PDF 渲不出来」，是「打印那句警告时编码炸了」。** 如果编码没炸，Windows 也会打印 WARNING 然后 PASSED。

**净结果：这一轮改动的核心（换成 QPdfWriter 让离屏渲染可用）没有任何一次成功渲染的证据。** 「没跑到 ≠ 通过」。

**裁决：**

1. ubuntu job 的 apt 列表加 `fonts-noto-cjk`。
2. `FontUnavailableError` 在 CI 里**必须是失败**，不许降级成 WARNING。那个 `try/except/else` 整个删掉，直接 `render_pdf(...)` 然后断言。
3. 两个 job 都必须打印 `PDF OK: <N> bytes, header=b'%PDF'`，并且断言 `N > 2000`（一份含表格的 A4 报告不可能只有几百字节；`> 0` 挡不住「渲出一张空白页」）。
4. 步骤末尾加一条断言：PDF 字节里能找到 `report.declaration` 第一行的 UTF-16BE 或 PDF 文本编码形式过于脆弱，改用可靠的做法——**把 `render_pdf` 生成的 HTML（`_report_to_html`）单独断言**含声明第一行，再断言 PDF 头和体积。判断在模型层，渲染只证明它没崩。

### C2（最重）字体检测的口径是错的，会对着一台正常的机器说「本机缺中文字体」

Windows job 的 traceback 落点很明确：

```
File "...\export_pdf.py", line 96, in _select_font_with_qt
    chosen = select_cjk_font(families)
File "...\export_pdf.py", line 60, in select_cjk_font
    raise FontUnavailableError(
FontUnavailableError: 本机缺中文字体，已找过这三个：Microsoft YaHei, SimSun, Noto Sans CJK SC；...
```

抛在**第 60 行**，也就是纯函数 `select_cjk_font` 里的名字匹配——`QFontDatabase.families()` 返回的列表里**没有这三个名字中的任何一个**（大小写不敏感的精确匹配）。于是产品的反应是：拒绝导出，并告诉用户「你的机器缺中文字体」。

这句话在这台机器上是不是真的，我们并不知道——**我们只知道它的字体名不叫这三个名字。** Windows 上可能叫 `Microsoft YaHei UI`、中文系统上可能报 `宋体`；Linux 上常见的是 `Noto Sans CJK JP`（同一套字形，只是 family 名不同）或 `WenQuanYi Zen Hei`。**用三个硬编码的名字来回答「这台机器能不能渲中文」，口径本身就是错的。**

更糟的是，代码里**已经有**正确口径的函数，却被放在错误的位置：

```python
def _check_font_renders(family: str) -> bool:
    try:
        db = QFontDatabase()                    # ← Qt6 里 QFontDatabase 成员全静态，实例化没有意义
        font_id = db.addApplicationFont("")     # ← 空路径，「触发初始化」是想象出来的效果
        raw = QRawFont.fromFont(...QFont(family))
        return raw.isValid() and raw.supportsCharacter(_TEST_CHAR)
    except Exception:
        return False                            # ← 探针崩了 = 「这个字体渲不了中文」
```

三个问题叠在一起：① 它只在名字匹配**成功之后**当二次过滤，名字匹配失败时它连运行的机会都没有；② `QFontDatabase()` + `addApplicationFont("")` 这两行在 Qt6 下是无意义甚至会抛的调用；③ 整个函数包在 `except Exception: return False` 里——**任何内部故障都会被翻译成「这个字体渲不了中文」，然后向用户输出一句关于他机器的、我们没有验证过的判断。** 静默兜底比报错危险。

**裁决（口径反过来）：**

1. `_check_font_renders` 修好并提升为**唯一判据**：枚举 `QFontDatabase.families()`，对每个 family 用 `QRawFont.fromFont(QFont(f)).supportsCharacter("中")` 实测，收集所有能渲中文的 family。
2. `CJK_FONT_CANDIDATES` 三个名字降级为**优先级排序**：能渲中文的集合里如果有候选名（大小写不敏感、允许 `startswith` 匹配以吃下 `Microsoft YaHei UI`），优先用它；否则用能渲中文的集合里的第一个。
3. **只有当没有任何 family 能渲「中」时**才抛 `FontUnavailableError`，报错信息里要带上「我枚举到了 N 个字体，没有一个能渲『中』」，N 是实测数字。
4. 删掉 `QFontDatabase()` 实例化和 `addApplicationFont("")`。`except Exception` 收窄成具体异常类型，并且**把异常内容带进报错信息**——探针自己坏了和字体真的不行，是两件必须能区分的事。
5. 纯函数的边界保持（这个设计是对的）：`select_cjk_font(能渲中文的 family 列表)` 仍然是纯函数、仍然可在沙箱测；只是**输入从「系统装了哪些字体」改成「哪些字体实测能渲中文」**。

> 另有一条不在你范围内、我会在集成时给 B10 下单：研究版安装包应当**自带一份 CJK 字体**（Noto Sans SC，OFL 许可，可随包分发）。一个交给国内实验室的产品，能不能出 PDF 不该取决于对方机器装了什么字体。你只需要把上面的检测口径改对，并且在候选列表里给「随包字体」留第一优先级。

### C4 台账 16 个读数里 3 个是装饰

`test_validation_readings_match_documents` 的做法是「值的字符串形式出现在来源文件里」。对小整数，这个条件几乎是恒真的。我逐个实测了 16 个读数：

| 读数 | 值 | 在来源文件里出现次数 | 把它改成邻近的错值，守卫会红吗 |
|---|---|---|---|
| `own_n_trials` | 27 | 88 | **不会**（"28" 也在文件里） |
| `own_n_paired` | 26 | 226 | **不会**（"27" 也在文件里） |
| `own_pass_n` | 5 | 33 | **不会**（"6" 也在文件里） |
| `csi_n` | 27 | 4 | 会（"28" 恰好不在——靠运气） |
| 其余 12 个（`+1.74` / `0.933` / `35.15` / `0.842` / `466.88` / `99.923` …） | — | 1–5 | 会 |

被漏掉的这三个正是最容易被写错的那三个：**试次数 27、可配对 26、通过 5**——它们要进研究版的声明文案，是给客户看的数字。

**裁决：** `__sources` 的条目从一个字符串升级成三段：

```json
"own_n_trials": {
  "file": "docs/ISSUES.md",
  "anchor": "DP-055",
  "quote": "<从文件里逐字抄一小段，含这个数字>"
}
```

守卫改成：`quote` 必须逐字出现在 `file` 里；`str(value)`（含符号变体）必须出现在 `quote` 里；`anchor` 必须出现在 `quote` 所在的那一行或其上文 20 行内。这样 16 个读数**每一个**都被钉在一句具体的话上，改值必红，改小整数也必红。16 条改起来是抄写量，不是设计量。

### C6 inline `python -c` 里打印中文，Windows 上必炸

Windows job 那条 `UnicodeEncodeError: 'charmap' codec can't encode` 是 DP-108 A1 的同族问题，但**边界不同**，两边不要互相「顺手清理」：

| 场景 | 归一化在哪 |

`desktop-selftest.yml` 的 export smoke 步骤属于第二类 ⇒ 加 `env: PYTHONUTF8: "1"`。

### C7 `render_pdf` 失败时，xlsx 和审计包已经写出去了吗

`FontUnavailableError` 的消息说「xlsx 与审计包不受影响，可以先导那两个」——这句话在 CI 日志里被证实（`xlsx OK: 8634 bytes` 打在异常之前）。但**用户视角的行为没有被定义**：点「导出报告」之后，如果 PDF 失败，用户手里是三份齐全、还是两份加一个错误框？目录里会不会留下一个 0 字节的 `.pdf`？

**裁决：** 导出层给出明确契约并各配一条测试：三份产物**要么都在，要么都不在**（先渲染到临时目录，三份都成功才原子移动到目标目录）；PDF 失败时不许在目标目录留任何半成品；错误框里说清楚「另外两份也没有导出，修好字体后重试」。**半成品目录比一个明确的失败危险。**

### C8 「声明三处同源」这条守卫，一处只看标题行，另一处根本没看

`test_declaration_same_source_in_all_three_outputs` 的名字和 docstring 都说「xlsx / PDF 内容层 / 审计包声明.txt **三份字符串逐字相同**」。实际断言：

| 出处 | 断言 |
|---|---|
| 审计包 `声明.txt` | `decl_in_zip == decl` — **逐字相等，有牙** |
| xlsx | `first_line in all_text` — **只查第一行 `### 研究用途声明` 是不是子串** |
| PDF | **一条都没有** |

也就是说：xlsx 只要写上「### 研究用途声明」这一行标题、把底下整份声明（「没有计量资质」「秒数不得作为计量结果」「分母不看，秒数没有意义」全都在里面）**全部删掉**，这条守卫依然全绿。而 PDF 那一份完全在守卫视野之外——它是三处里唯一还没被任何测试碰过的。

这件事严重是因为**声明就是这个产品的合规边界**。研究版能不能发，靠的不是代码，是这段话在每一份产物里都在。

**裁决：**

1. xlsx 那半边改成**逐字相等**：把声明所在的连续单元格按行拼回一个字符串，断言 `== report.declaration`（`_write_declaration` 是按 `splitlines()` 逐行写的，拼回来是确定的）。
2. PDF 那半边：`_build_html(report)` 是纯函数、不需要 Qt，**在沙箱里就能测**。断言 `report.declaration` 的每一行都出现在 HTML 里（HTML 转义后比对）。这一条现在就能加，不必等 CI。
3. 测试名与 docstring 说「三处」，那就必须真有三处断言。**注解不是校验。**

### C9 `EXPORT_SUFFIXES` 一个产品读者都没有，被守着的是那份死的

```python
EXPORT_SUFFIXES: dict[str, str] = {
    "xlsx":      "{stem}_" + _MODE_RESEARCH + ".xlsx",   # ← 写死 research
    ...
}

def export_paths(exp, video_index, mode):
    mode_str = mode.value                                 # ← 这里才是真的
    return {"xlsx": out_dir / f"{stem}_{mode_str}.xlsx", ...}
```

`grep -rn EXPORT_SUFFIXES --include='*.py' .` 的结果：定义 1 处（`export.py`），读者 **0 处产品代码**，其余全在 `tests/test_export.py` 和 `tests/test_report_model.py` 里。**决定客户拿到的文件叫什么名字的是 `export_paths()`，它自己又拼了一遍。** 于是：

- 文件名模板有**两个来源**，而且它们**已经不一致**了——`EXPORT_SUFFIXES` 永远是 `research`（`_MODE_RESEARCH` 写死），`export_paths` 用 `mode.value`。计量版一旦出现，`EXPORT_SUFFIXES` 就是一份错的声明。
- 三条围着 `EXPORT_SUFFIXES` 的守卫（`test_export_suffixes_contain_mode_value`、`test_research_literal_not_hardcoded_in_export_suffixes`、`test_research_suffix_derived_from_mode_enum`）**全部只读那个没人用的 dict**——「一条断言自己 mock 的测试」的变种：断言的是一份摆在那里给测试看的声明，不是产品的行为。
- `test_export_suffixes_contain_mode_value` 里 `assert ".pdf" in EXPORT_SUFFIXES["pdf"]` 用的是子串：改成 `.pdfx` 它照样绿（见 §5 N3）。

**裁决：** 二者合一，只留一个来源。`EXPORT_SUFFIXES` 改成**与 mode 无关的模板**，由 `export_paths` 唯一消费：

```python
EXPORT_SUFFIXES: dict[str, str] = {
    "xlsx":      "{stem}_{mode}.xlsx",
    "pdf":       "{stem}_{mode}.pdf",
    "audit_zip": "{stem}_{mode}_审计包.zip",
}

def export_paths(exp, video_index, mode):
    ...
    return {k: out_dir / v.format(stem=stem, mode=mode.value)
            for k, v in EXPORT_SUFFIXES.items()}
```

守卫跟着改成**盯行为**：`export_paths(..., Mode.RESEARCH)` 与 `export_paths(..., Mode.VALIDATED)` 各跑一次，断言三个文件名逐字等于预期（预期字符串写在测试里），并断言 `export.py` 里没有第二处拼接文件名的地方（AST 找 `JoinedStr` 里含 `.xlsx` / `.pdf` / `.zip` 的，只许出现在 `EXPORT_SUFFIXES` 的定义里）。**一个门槛只许有一个来源**，文件名也是。

### C10 后缀黑名单用的是「字符串完全相等」，粘一个字就看不见了

`test_export_suffixes_only_in_export_py`：

```python
if node.value == lit_val:     # lit_val 是 ".xlsx" / ".pdf" / "_research" / "_审计包"
```

**完全相等**。而 f-string 在 AST 里是 `JoinedStr`，它的字面部分是「占位符之间的那一段」——`f"{stem}.xlsx"` 的常量部分恰好是 `".xlsx"`（抓得到），但 `f"{stem}_导出.xlsx"` 的常量部分是 `"_导出.xlsx"`（**抓不到**）。也就是说：**页面层只要在后缀前面粘一个字，就可以自己拼文件名，守卫全程失明**（§5 N14 实测装饰）。

同一个毛病也让 `export.py` 自己的 `f"{stem}_{mode_str}_审计包.zip"` 逃过了「`_审计包` 只许在本文件」这条声明——它在本文件里是允许的，但说明了黑名单的形状不对。

**裁决：** 判据从 `==` 改成 `in`（子串），并把 `.zip` 也加进名单。改完拿 `f"{stem}_导出.xlsx"` 打一遍变异，证明它红。**一个只查完全相等的黑名单，挡不住把后缀和别的字粘在一起的人**——这和 B7 那边 A6（把门槛数字写进字符串躲开 float 黑名单）是同一件事的第二次出现，我把它记进 `_共同约定_v1.md`。

### C11 测试会去改 `data/validation_readings.json` 这份被 git 跟踪的文件

```python
def test_declaration_numbers_from_json_not_hardcoded() -> None:
    original = VALIDATION_READINGS_PATH.read_text(encoding="utf-8")
    try:
        ...write_text(json.dumps({**original_data, "own_bias_s": "+999.99"}, ...))
        ...
    finally:
        VALIDATION_READINGS_PATH.write_text(original, encoding="utf-8")
```

这条测试的**思路是对的**（改 JSON → 报告必须跟着变，这才叫「数字不是写死的」），但它把工作区里一份**被 git 跟踪、要进产品的数据文件**当成了临时文件。`finally` 挡得住断言失败，挡不住 `KeyboardInterrupt` 之外的进程被杀、磁盘写一半、或者两个人同时跑测试。一旦没恢复，**仓库里躺着一份声明写着「总体偏差 +999.99 秒」的产品数据，而且 CI 会绿**（测试自己会把它改成 +999.99 再断言）。

**裁决：** `report.py` 的读取路径改成可注入（模块级 `VALIDATION_READINGS_PATH` 允许测试 monkeypatch，或 `render_declaration(..., readings_path=None)` 多一个只给测试用的参数）。测试把 JSON **复制到 tmpdir 改副本**，产品文件一个字节都不许动。改完在 §4 报告里贴 `git status --porcelain data/` 在测试跑完后为空。

### C12 导出失败时，弹窗标题写的是「导出完成」

`pages/results.py::_on_export`：三个导出各包一个 `except Exception`，把错误攒进 `errors`，最后：

```python
if errors:
    QMessageBox.warning(self, "导出完成（有警告）", "\n".join(errors))
else:
    QMessageBox.information(self, "导出成功", f"已导出到：{out_dir}")
```

三个全失败时，用户看到的标题是**「导出完成（有警告）」**。目录里可能一个文件都没有。这是 A2 那件事在另一个页面上的复发：**结论区不为空，但里面那句话是假的。**

另外两件连着的：

1. **没有原子性。** xlsx 成了、审计包炸了，用户手里是一份没有审计包的报告，而弹窗说「完成」。
2. **`except Exception` 太宽。** 我们自己代码里的 `KeyError` / `TypeError` 会变成弹窗里的一行字，标题仍然是「完成」。**静默兜底比报错危险。**

**裁决：**

1. 标题按实际结果分三档：全成 →「导出成功」；部分成 →「**部分导出失败**」并逐条列出**哪几份成了、哪几份没成**；全失败 →「**导出失败**」。
2. 三份产物先渲染到 `out_dir` 下的临时子目录，三份都成功才移动到 `out_dir`；任何一份失败就整体不留（`FontUnavailableError` 也一样——**要么三份都在，要么一份都不在**）。这条替换我上一版意见里的 C7，口径不变，落点更明确。
3. `FontUnavailableError` 单独接住给友好文案（这个已经做了，保留），其余 `Exception` 也接住，但弹窗里要写明「这是软件内部错误，请把这段话发给我们」，并且**标题必须是「导出失败」**。

> 这一段和 B7 那边的 A2 是同一句话的两次出现，一起记进 `_共同约定_v1.md`：**任何给用户看结论的地方，「不为空」不是要求，「说的是真话」才是要求。**

### C13 页面把发布态写死成 `None`，计量版那条路从界面上走不到

### C14 审计包的名册：缺一条可以不记，未知可以写成 0，都没有守卫

`export_audit.py` 的设计意图是对的（「取不到的字段写 null + 原因，不许悄悄少装」写在文件头的注释里）。但守卫只验了 `声明.txt` 那一条的 sha256 / size，于是意图本身没有被钉住。三处实测：

| 变异 | 结果 |
|---|---|
| N10：`_manifest_entry` 的缺失分支 `"sha256": None, "size": None` → `"sha256": "", "size": 0` | **装饰** |
| N11：引擎产出缺失时，`manifest_entries.append(...)` 整条删掉（名册里干脆不记） | **装饰** |
| N15：`声明.txt` 不放进 zip（MANIFEST 仍记着它） | 红 3（`test_audit_zip_manifest` 等） |

第三行说明「名册记了但实物不在」抓得住（因为守卫会去 `zf.read("声明.txt")`）。前两行说明**反方向完全没守**：

1. **N10** 把「取不到」变成「sha256 是空串、大小是 0 字节」——这正是本仓第一条铁律的反例。**未知不许长成数字的样子**，尤其在一份叫「审计包」的东西里：`size: 0` 是一句关于文件的陈述，`null` 才是「我们没有这个文件」。
2. **N11** 更彻底：引擎四个产出里缺了哪个，名册里连一行都没有。客户打开审计包看到 MANIFEST 里整整齐齐五条，**看不出少了一条 timeline_csv**——「坏掉的名册长成了一份看起来完整的名册」。而这条路径（引擎产出缺失）**一条测试都没有**，`test_audit_zip_manifest` 只跑了全都在的那种情况。

**裁决：**

1. 新增守卫 `test_audit_manifest_reconciles_with_zip`：**双向对账**。
   - 名册里 `sha256` 非 null 的条目集，必须与 `zf.namelist()` 逐个相等（含 `MANIFEST.json` 自己）；
   - `sha256` 为 null 的条目**必须不在** namelist 里，且 `missing_reason` 非空；
   - namelist 里不许有名册上没有的成员。
2. 新增守卫 `test_audit_manifest_records_missing_engine_outputs`：构造一个 `engine_output_paths` 指向不存在文件的 Report，断言 MANIFEST 里**恰好有四条**（四个引擎产出的键各一条）、每条 `sha256 is None and size is None and missing_reason` 非空，并断言 `missing_reason` 里含那个路径。
3. `_manifest_entry` 的 null 字段加一条守卫：AST 或直接断言缺失条目的 `sha256` / `size` 必须 `is None`（不许是 `""` / `0` / `-1`）。改完拿 N10 打一遍，必须红。
4. 顺带一个形状问题：缺失条目的 `name` 现在写成 `"[csv]"` / `"[self_test.json]"`（方括号包着键名），**和实际文件名不是同一个命名空间**。名册里应该写「本该叫什么」——请改成把 `export_paths` / 引擎 `OUTPUT_SUFFIXES` 推出来的**预期文件名**，取不到预期文件名时才退回键名，并在 `missing_reason` 里说明。客户拿着名册要去问「那个 timeline_csv 呢」，`[timeline_csv]` 这四个字帮不上他。
