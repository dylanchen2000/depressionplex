## 1. 必须改

### A1（最重）一个问题四种机制、九份拷贝，而那条叫「单一来源」的守卫要求的正是这九份

现状，同一个「Windows 上中文往 stdout 一写就炸」的问题，仓里有四种答法：

| # | 位置 | 机制 | 覆盖面 |
|---|---|---|---|
| 1 | `depressionplex/cli/*.py` **九个 main()** | `sys.stdout.reconfigure(encoding="utf-8")` + `sys.stderr…`，每处都带 `# type: ignore[attr-defined]` | 九份逐字拷贝 |
| 2 | `desktop/main.py:21-25` | `io.TextIOWrapper(sys.stdout.buffer, encoding="utf-8", errors="replace")`，且 `if sys.platform == "win32"` 才做 | 外壳 |
| 3 | `.github/workflows/build-windows.yml` | `env: PYTHONUTF8: 1` | 只有构建机 |
| 4 | `packaging/fetch_ffmpeg.py` | **什么都没做**，靠第 3 种 | run #1 就是死在这里 |

四种机制里，第 1 种的九个 `# type: ignore[attr-defined]` 是**九次自白**：类型检查器说的是实话——
`sys.stdout` 不保证有 `reconfigure`——而它警告的事立刻就发生了，就是 §0 里那三条红。
`io.StringIO` 没有 `reconfigure`，任何把 stdout 换成 `StringIO` 来抓输出的测试，一进 `main()` 就 `AttributeError`。

而 `test_cli_encoding_reconfigure_single_source` 这条守卫：

- 它的名字和 docstring 说「**且不许有第二处**」；
- 它的身体要求的是：`depressionplex/cli/` 下每一个有 `main()` 的文件，`main_func.body[:5]` 里**必须**出现一个 `stdout`/`stderr` 的 `.reconfigure` 调用；
- 「不许有第二处」这句话，代码里**一个字都没有验**。

实测三条：**M8** 把 `analyze.main` 里两行 reconfigure 全删 ⇒ 红 1（就是它，它唯一真会红的方向）；
**M7** 只删 `sys.stderr` 那一行、留下 `sys.stdout` ⇒ **不红**（`stderr` 上的中文照样能崩，而它满足了「二者之一在」）；
**M13** 在 `depressionplex/runner.py` 顶层加**第二处** `reconfigure` ⇒ **不红**。
也就是说：**这条守卫的名字说的是「只有一处」，它的身体要求的是「九处都要有」，而它实际能挡的只有「一处都没有」。**
它不但没有阻止重复，它把重复钉死了——想把九份收成一份（抽个 `force_utf8()` 出来调用），
第一件被拦下的事就是这条守卫，因为 `force_utf8()` 不是一个 `.reconfigure` 属性调用。
**一条把缺陷固化下来的守卫，比装饰更糟。**

裁决（第五轮按这个写）：

1. 新增 `depressionplex/cli/_stdio.py`，**只此一处**：

   ```python
   def force_utf8() -> None:
       """把本进程的 stdout/stderr 切成 UTF-8。取不到 reconfigure 就什么都不做。

       Windows 客户机默认 cp1252/cp936，中文报告会 UnicodeEncodeError（不是乱码，是崩）。
       **必须防御式取**：测试会把 stdout 换成 io.StringIO，它没有 reconfigure；
       而 StringIO 本来就是 unicode 干净的，不需要切。
       """
       for stream in (sys.stdout, sys.stderr):
           fn = getattr(stream, "reconfigure", None)
           if fn is not None:
               fn(encoding="utf-8")
   ```

2. 九个 CLI 的 `main()` 第一条可执行语句改成 `force_utf8()`，`# type: ignore` 全部删掉；
3. 守卫改成**名副其实**的两半：
   - 每个有 `main()` 的 CLI，其 `main()` 的**第一条可执行语句**必须是 `force_utf8()` 调用（不是「前 5 条里有」——前 5 条里有，意味着可以在它前面先 `print` 一句中文）；
   - **除 `_stdio.py` 外，整个 `depressionplex/` 与 `packaging/` 不许出现 `.reconfigure(`**。这才是「只有一处」。
4. `packaging/fetch_ffmpeg.py` 也调 `force_utf8()`（它 import 不到 `depressionplex` 就自己写三行，但要在守卫的名册里）。
   **不许靠 workflow 的 `PYTHONUTF8: 1` 兜着**——那个环境变量只存在于构建机，客户机上没有；
   而且它现在的副作用是：**九处 `reconfigure` 在 Windows 构建里全是空操作，构建 CI 因此永远发现不了编码回归。**
5. 外壳那份（机制 2）保留，但注释要写清为什么**故意**不一样：`errors="replace"` 是刻意的（自检宁可打出乱码页名，也不许以「崩溃」的形式失败），而引擎那边要的是真报错。
   外壳不许 import 引擎（架构 §3.4），所以两边不可能共用代码——那就各留一处，**各只留一处**，并在守卫里点名这两处是全仓唯一的两个。
6. §0 那三条红必须变绿。

### A4 H9 只改了一半：`ffprobe` 的来源被 `_` 丢掉了，而 `ffprobe` 决定计分窗口

`analyze.py:main`：

```python
ffmpeg_path, ffmpeg_source = video._resolve_ffmpeg_tool("ffmpeg")
ffprobe_path, _ = video._resolve_ffmpeg_tool("ffprobe")   # ← source 丢了
```

`run.json` 的 `decoder` 块于是长这样：`{ffmpeg_path, ffprobe_path, source, ffmpeg_version}`——
**一个 `source`、一个 `version`，说的都是 ffmpeg**，而 `ffprobe_path` 旁边什么都没有。

这不是洁癖问题：`probe()` 用的是 **ffprobe**，它产出 `fps`、`n_frames`、`frame_count_source`——
也就是**计分窗口的边界和每一秒的归属**。审计包里那句「这批帧是哪个解码器解出来的」，
现在对**量出帧数的那个工具**是沉默的，却又用一个单数的 `source` 字段断言了一个确定的来源。

而混着来是真的能发生的：解析器对两个工具**各解析一次**，
只设 `DPX_FFMPEG` 不设 `DPX_FFPROBE`，或者随包目录里 `ffmpeg.exe` 在而 `ffprobe.exe` 不在（安装包漏一个文件就是这样），
就会得到「随包的 ffmpeg + 客户机 PATH 上不知道哪个版本的 ffprobe」，而 `decoder.source` 写着 `"bundled"`。
**未知不许长成一句确定的判断**——上一轮 H9 的原话就是「解析器必须返回路径 + 来源、**两个工具各有自己的 source**」。

裁决：

```json
"decoder": {
  "ffmpeg":  {"path": "...", "source": "bundled", "version": "ffmpeg version 8.1.2 ..."},
  "ffprobe": {"path": "...", "source": "system",  "version": null},
  "mixed_source": true
}
```

- 两个工具各自 `path` / `source` / `version`（`ffprobe -version` 与 ffmpeg 同样取法）；
- 两边 `source` 不同时，`mixed_source` 为真，**并往 stderr 写一行 `[警告]`**：这在科学上就是一次可疑的运行，报告里应该看得见（B6 那边的审计页顺手印上）；
- 取值集合收成 `video.py` 里一个 `DECODER_SOURCES = ("env", "bundled", "system")`，`analyze.py` 里那句注释 `# "env" | "bundled" | "path"` 删掉——**它写的 `"path"` 是解析器从来不会返回的值**，解析器返回 `"system"`。一个取值集合两份说法，其中一份是假的，而没有任何守卫对过账。
- 守卫要能看见混着来：现在 `test_run_json_decoder_block` 把两个工具 mock 成同一个 `"env"`（`side_effect = lambda tool: (f"/fake/{tool}", "env")`），**按构造永远看不见 source 不一致**。第五轮至少三种情形：同源、混源、版本取不到。

实测四条，说明 `source` 这个字段今天**没有任何守卫**：

| 变异 | 结果 |
|---|---|
| **M4** `decoder_source = "bundled"` 写死字面量 | **不红** |
| **M5** `decoder_source = "whatever"`（一个解析器根本不会返回的取值） | **不红** |
| **M2** 随包档的返回值拼错成 `"beundled"` | **不红**（随包这一档从来没被正面断言过） |
| **M3** 解析顺序改成 PATH 先于随包 | **不红**（客户机上那个来路不明的 ffmpeg 会静静地顶掉我们随包的那个，而 `source` 会诚实地写 `"system"`——没人看） |

M3 这一条最值得单独看一眼：它**不是**一个「守卫写松了」的问题，它是**优先级顺序本身没有守卫**。
而这个顺序决定的是「客户跑出来的那批帧是哪个 build 解的」，也就是 G7/G8 那批数字还算不算数。
第五轮三条：三档各一条正面断言（env / bundled / system 各返回什么 source、路径取哪个），
外加一条顺序断言（三者同时存在时必须得到 `env`；只有后两者时必须得到 `bundled`）。

### A5 守卫 9 断言的是它自己 mock 的返回值

`test_run_json_decoder_block` 的 docstring：「ffmpeg_version 取不到时是 None 不是 `""`」。
它的身体：

```python
with patch("depressionplex.cli.analyze._get_ffmpeg_version") as mock_version:
    mock_version.return_value = None
    ...
    assert decoder["ffmpeg_version"] is None
```

**它把它声称要守的那个函数整个 mock 掉了**，然后断言字典里出现了自己塞进去的 `None`。
`_get_ffmpeg_version` 真的改成 `return ""`，这条守卫**不会红**（变异 M6 实测，见 §5）。

改法：`_get_ffmpeg_version` 自己要有一条直测——喂一个不存在的路径、喂一个 `returncode != 0` 的假可执行、喂一个只输出空行的假可执行，三种都断言 `is None` 且 stderr 有一行 `[警告]`。
`_build_run_json` 那边保留 mock（它测的是「None 有没有原样落进 JSON」，那是另一件事），但 docstring 要改成它真正在测的那句话。

### A6 守卫 12 要求违规者先把路径分隔符写进去，它才肯看见

`test_bin_extraction_no_hardcoded_dll_list` 的筛子是：

```python
if '.dll' in s and ('/' in s or '\\' in s):
```

**必须同时含 `.dll` 和一个路径分隔符**，才进入检查。
而任何人硬编码 DLL 名单，写出来就是 `["avcodec-62.dll", "avfilter-11.dll", …]`——**没有路径分隔符**。
也就是说：这条守卫防的是最不像的那一种写法，最像的那一种它看不见（变异 M9 实测）。

去掉分隔符这个条件（`'.dll' in s` 就够），并且把最后那句子串汤

```python
assert "bin/" in src and "for " in src and "member" in src.lower()
```

改成 AST：`main()` 里必须存在一个遍历 `namelist()` 的循环，且 `bin_prefix` 参与了成员筛选。
现在这三个子串在**注释里**也能满足。

### A7 为 H1 写的元守卫，看不见 H1 那行代码

`test_no_module_level_patches` 的判据是「模块顶层赋值，且属性链的根 `Name` 是 `depressionplex` 或 `desktop`」。
而 H1 那个缺陷的原形是 `tests/test_video.py` 顶层的

```python
video._resolve_ffmpeg_tool = lambda …
```

`test_video.py` 的 import 是 `from depressionplex import video as V`——**属性链的根叫 `V`，不叫 `depressionplex`**。
换个别名，或者写 `from depressionplex import video` 再 `video.X = …`，这条元守卫一律看不见（变异 M11 / M12 实测）。
**一条为某个缺陷而写、却看不见那个缺陷本来长相的守卫，等于没写。**

改法：不要按根名字匹配。**`tests/*.py` 模块顶层一律不许有属性赋值**（`X.y = …`，depth 0），不管 `X` 是什么。
这个套件里没有任何一个正当理由需要它；真出现了正当需求，那时再加白名单，白名单旁边写理由。
判据从「猜它是不是引擎」变成「顶层不许改任何对象的属性」，别名就再也绕不过去。

### A8 冻出来的两个 exe 从来没被启动过一次

这一单的守卫全是**静态解析** spec / `.iss` / workflow 的文本，这是对的（沙箱没有 Windows）。
但静态守卫能证明的上限是「我们写的字对得上」，证明不了「装出来能跑」。
而这一类缺陷——少一个 DLL、hiddenimports 漏一个、`backend\` 放错位置——**只在启动那一刻现形**。

Windows runner 上补三步 smoke，都是几秒钟的事，**这是本轮性价比最高的一项**：

| 步骤 | 判据 | 能顶掉的一整类问题 |
|---|---|---|
| `vendor\ffmpeg\ffmpeg.exe -version` | 退出码 0 | shared 构建缺任一 DLL 会当场起不来 ⇒ 不再需要任何 DLL 名单 |
| `dist\depression-analyzer\depression-analyzer.exe --help` | 退出码 0 | 后端 hiddenimports 漏、`excludes` 误删 |
| `dist\DEPRESSION-PLEX\DEPRESSION-PLEX.exe --self-test`（`QT_QPA_PLATFORM=offscreen`） | 退出码 0 | GUI hiddenimports 漏、qss 没打进去、七页构造不起来 |

### A10 两个 spec 都 `upx=True`，而 runner 上没有 upx

### A12（架构裁决，不是缺陷）后端 exe 的入口只有 `analyze.py`，所以它永远接不了 `acq-check`

`build_analyzer_windows.spec` 的 `Analysis(["../depressionplex/cli/analyze.py"])`，`EXE(name="depression-analyzer")`。
冻结后的 `depression-analyzer.exe` 的 `main()` 就是 `analyze.main`，它的 argparse **没有子命令**。
而 B7（PR #97）那边已经写下了 `desktop/app/services/engine.py::acq_check_argv`，其冻结分支拼的是
`[<engine exe>, "acq-check", …]`——**这个约定不存在，而且按现在的打包方式不可能存在**。
（我已在 B7 第一轮意见里让它把 `acq_check_argv` 整段删掉；这里补上打包侧的根因。）

顺带一个数字，说明 `cmd[:-1]` 那种切片为什么必须禁掉：`engine_command()` 源码模式返回**三个**元素
（`[python, -m, depressionplex.cli.analyze]`），冻结模式返回**一个**（`[exe]`）。同一个切片在两种模式下切掉的是完全不同的东西。

裁决（**本轮由 B10 做**，因为它属于冻结契约）：

1. `depressionplex/cli/__init__.py` 加一个 `main()`：**子命令分发器**，名册是一个显式的字典
   `SUBCOMMANDS = {"analyze": …, "acq-check": …}`（先只放 `analyze`，`acq-check` 待 #97 合入后加）；
2. 后端 spec 的入口改成这个分发器；
3. `engine_command()` 两个分支改成
   - 源码：`[sys.executable, "-m", "depressionplex.cli"]`
   - 冻结：`[str(engine_path)]`

   之后**两种模式的 argv 形状一致**：`engine_command() + [子命令] + 参数`。`build_argv` 里多一个字面量 `"analyze"`，切片永远不需要。
4. 一条守卫：分发器的子命令名册 ⊆ `depressionplex/cli/` 下真有 `main()` 的模块，且外壳侧用到的子命令名必须在名册里（外壳不许 import 引擎，所以是 DP-114 那种镜像 + 对账）。

选它而不是「再冻一个 exe」的理由：第二个 exe 会把 numpy 和 PyInstaller 运行时再复制一份（每份约 40–60 MB），
而安装包本来已经背着 ffmpeg 的七个 DLL（约 165 MB）和整套 PySide6。为了一个自检页翻一倍体积，不值。

### A13 `autobuild-2026-09-13-14-50` 这个 tag 会消失，钉哈希也救不了

`FFMPEG_URL` 现在钉在 BtbN 的 autobuild release 上。它比 `latest` 好得多（上一轮 H2 就是这个），
但 BtbN 的 autobuild release 是**滚动清理**的：老的 autobuild tag 会被删掉。
到那天，`urlretrieve` 拿到 404，`build-windows` 直接失败——而钉哈希的**全部目的**就是「以后重建能得到同一份东西」。
一个几个月后就 404 的 URL，钉了哈希也不叫可重建。

改法：把那份 zip（80,114,619 字节，SHA256 `8bb18e29…38c9`）**镜像成我们自己仓的一个 Release asset**
（公司规矩：大文件不进 git，进 Release），`FFMPEG_URL` 指向我们的镜像，
上游 URL 作为**出处**留在注释里（法律上要能说清这份 LGPL 二进制是从哪来的）。
哈希不变——镜像的正确性由现有的哈希校验来保证，这正好是它该干的活。

### A14 H11 没改完：守卫 7 看不见真正起进程的那一行

上一轮 H11 要的是「不许在 `video.py` 之外用字面量 `"ffmpeg"` / `"ffprobe"` 起进程」。
新增的 `test_no_hardcoded_ffmpeg_invocation`（守卫 7）只认一种形状：
`subprocess.<something>` 的调用，且第一个实参是**列表字面量**，且列表第一项是常量 `"ffmpeg"`/`"ffprobe"`。

而这个仓真正起进程的地方**不是那个形状**：`video.py` 里是 `_run(cmd)` 和 `subprocess.Popen(cmd)`——
参数是一个 `Name`，不是列表字面量。所以：

**M1** 在 `probe()` 里插一句 `_run(["ffprobe", "-version"])`（绕过解析器、直接用 PATH 上的 ffprobe 起进程，正是 H11 要禁的事）⇒ **不红**。

守卫要改成两条，都不依赖调用点的写法：

1. **除 `video.py` 与 `packaging/` 外，`depressionplex/` 的任何源文件里不许出现字符串常量 `"ffmpeg"` / `"ffprobe"` / `"ffmpeg.exe"` / `"ffprobe.exe"`**（`video.py` 自己的 `_resolve_ffmpeg_tool` 是唯一入口，`tool_name` 由调用方传字面量进去，所以 `video.py` 内部允许，别处一律不许）；
2. `video.py` 里凡是 `_run(...)` / `subprocess.Popen(...)` 的第一个实参，**其取值必须能追溯到一次 `_resolve_ffmpeg_tool` 的返回**——AST 追不动就退到更硬的一条：`video.py` 里除 `_resolve_ffmpeg_tool` 之外的函数体内不许出现上述四个字符串常量。第 2 条能落地就落地，落不了地就只写第 1 条，别写一条看着像在管、实际只认一种写法的。
