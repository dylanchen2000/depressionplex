## §2 三条被改宽的守卫：变异实测

改宽守卫是本仓最危险的一类改动——红消失了不等于问题没了。这三条都是我点名要工人改的，
所以必须由我自己证明它们改完还有牙。每次只改**产品代码**，改成一个人真会不小心写出来的形状。

| 变异 | 改了什么（产品侧） | 变异前 | 变异后 |
|---|---|---|---|
| M1 | `analyze.py` 顶上加一行 `sys.stdout.reconfigure(encoding="utf-8")`（产品目录里的第三份 shim） | GREEN | **RED**「编码 shim 只许在两个 stdio 文件里」 |
| M2 | `_get_ffmpeg_version()` 里加 `subprocess.run(["ffprobe", "-version"])`（真的硬编码工具名） | GREEN | **RED**「发现硬编码的 ffmpeg 工具名」 |
| M3 | `decoder` 块删掉 `"mixed_source"` 一行 | GREEN | **RED**「decoder 块缺 mixed_source」 |

三次变异后都断言了文件已还原（`assert f.read_text() == orig`）——**永不还原的变异会架空后面所有守卫**（H1）。

M3 那条值得单说：`mixed_source` 不是装饰，它是「两个工具来源不同」时审计包要印警告的唯一依据
（只设了 `DPX_FFMPEG`、或随包漏了一个文件，都会发生）。丢了它，审计包会少说一句真话而且没人知道。

## §4 集成后我自己查出并修的两处

### 4.1 `acq-check` 的 UTF-8 垫片（`f0f705a`）

合 main 后 `test_cli_encoding_reconfigure_single_source` 红：`acq_check.py::main()` 第一条可执行语句不是
`_stdio.force_utf8()`。**这不是守卫太严，是真的集成缺口**——`acq-check` 的 stdout 全是中文，
冻结后在 Windows 上默认 cp1252，第一句 `print` 就 `UnicodeEncodeError`，GUI 侧只会看到「自检程序崩了」。
（`SUBCOMMANDS` 里加 `"acq-check"` 也在这一笔里；它只活在本分支，main 和 `feat/dp109-acq-check` 都没有这个常量，
所以 DP-109 那一轮只能记下、不能做。）

### 4.2 `_build_run_json` 的四个解码器实参 + 外壳侧 `decoder` 必写键（`7331468`）

CI @ `f0f705a` 的 `Tests` 红了四条（`34929592979`，通过 522 失败 4），全是同一个
`TypeError: _build_run_json() missing 4 required positional arguments: 'ffmpeg_path',
'ffmpeg_source', 'ffprobe_path', 'ffprobe_source'`。
**文本上合干净、语义上没合**：本单改了引擎的函数签名，main 通过 #97 带进来
`tests/test_results_model.py` 的四个旧签名调用方，git 看不见它们的关系。

**裁决：改测试，不给参数加默认值。** 依据在产品自己的 docstring 里（H10+A4）——调用方必须在分析开始前
就把解码器身份拿到手，否则会出现「数字算出来了但 run.json 崩了、CSV 也没有」；
`tests/test_progress_runjson.py` 开头第 7 条也早立过同一条规矩：「`scored` 不许有默认值
（有默认值 = 漏传时安静退回旧行为）」。给 `ffmpeg_path` 一个默认值，就是让「忘了传解码器身份」
悄悄过去，而 `decoder` 块里会写着一个谁也没解析过的路径。

四个调用点照产品那条路取身份：新 helper `_decoder_identity(tmp)` 走**真的**
`video._resolve_ffmpeg_tool`，env 变量指到 tmp 下两个真实存在的空文件。
不在测试里手写 `"system"`（手写等于给 `decoder` 块编一个产品永远不会写出来的值，那个块就再也没人验了），
也不照 `test_progress_runjson` 那样全局 patch 掉 `Path.exists`（本文件同一个 tmp 里还要真读真写
CSV 与 run.json，patch 掉会把「文件不在」这类失败一起盖住）。

**顺带闭了一个真缺口：** 引擎新增了顶层键 `decoder`，而 `desktop/app/models/results.py` 的
`required_top_keys` 里没有它。守卫 F5 的清单是「从真引擎产出的 run.json 取顶层键名生成（不许手写）」，
也就是说 F5 本来就要求两侧对齐——不加，F5 会红在 `decoder` 上，而**那不是 F5 太严**：
外壳真的会安静接受一份答不出「这批帧是哪个解码器解出来的」的 run.json。
这正是 DP-110 那个 `decoder_info` 永远打印「未知」的另一头。

变异（在 `tmp-dp108-f5-mutation` @ `5f97501` 上跑真 CI，已删分支）：把 `"decoder"` 从
`required_top_keys` 里拿掉 ⇒ `Tests` `34930629326` **failure，通过 525 失败 1**，
唯一一条红是 `test_results_model.test_f5_top_level_required_keys`，报
`AssertionError: 删掉 'decoder' 应该抛 ResultsError`。**点名到键。**
同一次运行里 `test_packaging_contract.test_run_json_decoder_block` 仍然 PASS ——
引擎侧那条守卫管不到外壳侧，两条守卫管的是两件事，这也是为什么两条都得有。

本单只做「`decoder` 必须在场」。把值读出来印到报告上、以及 `decoder` 的类型校验（`null` 目前还能过），
是 #96（DP-110）报告层的活，另立台账行，不在这里顺手做（一个分支一件事）。

## §6 版本号裁决

`docs/标定文件示例_研究版.json` 里的 `tool_version: "0.1.0"` **不跟** `pyproject.toml` 的 `1.0.0` 走，
`tests/test_progress_runjson.py` 里那个 `'0.1.0.dev0'` 夹具也不用改。理由：那个字段记的是
**签这份标定文件时的代码版本**，是历史事实；全仓没有任何地方拿它和「当前运行版本」比对。
把它改成 1.0.0 等于篡改一条记录，还会让「这份标定是哪版签的」永远答不出来。
