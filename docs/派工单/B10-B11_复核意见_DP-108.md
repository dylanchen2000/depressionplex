## 三、必须修的（按严重度排）

### H1 你自己加的两个模块级补丁，把守卫 6 变成了「测一个 lambda」

这一轮新增：

```python
tests/test_video.py:14            V._resolve_ffmpeg_tool = lambda tool: f"/fake/{tool}"
tests/test_progress_runjson.py:38 video._resolve_ffmpeg_tool = lambda tool: f"/fake/{tool}"
```

两处都在**模块顶层**，**永不还原**。而 `run_tests.py` 是**单进程**、按 `TEST_MODULES`
顺序 `importlib.import_module` 依次导入：`test_video`（第 24 行）→ `test_progress_runjson`（28 行）
→ `test_packaging_contract`（32 行）。所以守卫 6 里那句 `video._resolve_ffmpeg_tool("ffmpeg")`
调到的是**那个 lambda**，永远返回 `/fake/ffmpeg` —— 这就是 H0-a 那行 `AssertionError` 的全部成因。

**这条比「一条测试红了」严重得多**：它说明**一条守卫可以被另一个测试文件的导入副作用解除武装**。
本仓成文的规矩是「能被跳过的守卫等于装饰」；这里是它的升级版 ——
**能被邻居悄悄换掉的守卫，比装饰更糟，因为它看起来在测真东西。**
顺带一说，这个 lambda 同时也把 `test_video` / `test_progress_runjson` 后面那些真断言
一起架空了（它们从此不再经过真解析器）。

改法（三条都要）：

1. 两处模块级赋值**全部删掉**。要 mock 就在**每个用到的测试函数里**用
   `mock.patch("depressionplex.video._resolve_ffmpeg_tool", ...)` 作上下文管理器，
   或者 `try/finally` 手工还原。
2. **更好的办法是根本不 mock**：你自己刚做出了 `DPX_FFMPEG` / `DPX_FFPROBE` 这条正式的缝，
   沙箱里直接 `os.environ["DPX_FFMPEG"] = <一个真实存在的空文件>` 就够了 ——
   走的是产品代码的真路径，不是替换。（注意解析器要求 `Path(env_path).exists()`，所以要个真文件。）
3. 加一条**元守卫**：扫 `tests/*.py`，**模块顶层**（`ast.Module.body` 直接子节点）不许出现
   对 `depressionplex.*` / `desktop.*` 模块属性的赋值（`ast.Assign` 且 target 是 `ast.Attribute`）。
   这类补丁一旦出现在顶层就是全局污染，必须在测试层就被拦住。

### H2 下载地址指向一个**不存在的资产**，而且用的是会动的 tag

```python
FFMPEG_URL = "https://github.com/BtbN/FFmpeg-Builds/releases/download/latest/ffmpeg-n6.1.1-win64-lgpl-shared-6.1.zip"
```

我实测：这个 URL **HTTP 404**（跟完重定向仍是 404）。这个文件名下的资产不存在。

即使它存在也不能这么写：**BtbN 的 `latest` tag 是每天重新发布的**。
「把哈希钉死」+「用一个会动的 URL」= 某天构建突然失败，而失败的样子是
**「SHA256 不匹配」** —— 看起来像文件被篡改（安全事件），实际只是上游换了文件。
**钉哈希必须钉在不动的 URL 上，否则钉的是一个假的确定性。**

### H3 哈希是编的，而守卫 8 按构造发现不了

```python
# 占位哈希（首次真实构建前需手动下载 zip、计算实际 SHA256、替换这里）
FFMPEG_SHA256 = "45eb9e600e7a3d8760cbe8a67817842ed9b78bec961febc1bb9b4663087250ca"
```

守卫 8 查的是 `len(...) == 64` 与 `re.fullmatch(r'[0-9a-fA-F]{64}')`。
**一个编得像真哈希的占位，天生满足这两条。** 这条守卫对它要防的那一类东西完全无效。

这正是本仓「**未知不许长成数字的样子**」的教科书案例：
**占位必须长成 `None`**，让 `main()` 在下载之前就拒绝并报「哈希未钉，请先按 README 钉死」。
一个长得像真哈希的字符串，是这个文件里最危险的一行 —— 它让「还没钉」看起来像「已经钉好」。

守卫 8 另外两处要改：

- 它自己内联重写了一遍 sha256 计算，**没有调 `fetch_ffmpeg.sha256_file`** ⇒
  那个函数写错了它照样绿。改成调被测函数本身。
- 加一条：断言 `FFMPEG_URL` **不含 `/latest/`**（会动的 tag 一律红）。

我把 zip 的 `bin/` 数了一遍（字节数是实测）：

|---|---|
| `bin/ffmpeg.exe` | 540,672 |
| `bin/ffprobe.exe` | 226,816 |
| `bin/ffplay.exe` | 18,722,304（**不要**，我们不放视频） |
| `bin/avcodec-62.dll` | 90,160,640 |

`-shared` 的 exe 是**动态链接**的：这 7 个 DLL 缺任何一个，Windows 直接弹

—— 沙箱碰不到，CI 的 Windows runner 上也碰不到（那台机器 PATH 里另有 ffmpeg 的话更会掩盖掉）。

改法：**提取 `bin/` 下除 `ffplay.exe` 以外的全部成员**，加根下的 `LICENSE.txt`。

`.iss` 相应改成**一行**：

```
Source: "vendor\ffmpeg\*"; DestDir: "{app}\backend\ffmpeg"; Flags: ignoreversion
```

**顺带把这件事写进 `packaging/README.md` 的已知限制**：随包 ffmpeg 解开约 165 MB，
安装包体积会明显变大。这是「我们验过的解码器」换来的代价（§0.2 的理由），不是浪费 ——
但道俊需要知道装包有多大，请在交付报告里给出真构建后的安装包实际字节数。

### H9 `decoder.source` 是第二个派生器，而且**会印出假话**

`_resolve_ffmpeg_tool` 自己知道它走了哪条分支；`_build_run_json` 又用**另一套独立逻辑**
把答案重新推断了一遍：

```python
if os.environ.get("DPX_FFMPEG") or os.environ.get("DPX_FFPROBE"):
    decoder_source = "env"
```

两个可复现的假话：

1. `DPX_FFMPEG` 指向一个**不存在**的路径 ⇒ 解析器要求 `.exists()`，会跳过 env 走随包/PATH；
   而这里只看环境变量**非空** ⇒ **`source` 报 `"env"`，帧其实是别的 ffmpeg 解的。**
2. 只设 `DPX_FFPROBE`、不设 `DPX_FFMPEG` ⇒ ffmpeg 明明来自 PATH，也报 `"env"`。

**这个字段的全部用途就是回答「这批帧是哪个解码器解出来的」。它一旦会说谎，审计包就没有意义**
—— 而 B6 会把它印进客户报告（DP-110 §0.2）。这和 B4 那条 G1 是同一件事：
**未知（或未确认）不许长成一句确定的判断。**

改法：

- `_resolve_ffmpeg_tool` 返回**路径 + 来源**（小 dataclass 或 `(path, source)` 二元组）；
  `_build_run_json` 只**抄**解析器给的答案，一个 `if` 都不许自己判。
- **ffmpeg 与 ffprobe 各有自己的 `source`** —— 一个字段描述两个工具，天生不可能都对。
- 守卫：`DPX_FFMPEG` 指向不存在的路径 + 随包存在 ⇒ 断言 `source == "bundled"`。
  **这条新守卫在你现在的代码上应当先红**（现在会是 `"env"`）；先看它红，再修，再看它绿。

### H10 `_build_run_json` 里无保护地调解析器 ⇒ 算完了才炸，数字全丢

run.json 是**所有试次跑完之后**才写的。此处 `_resolve_ffmpeg_tool` 抛 `VideoError`，
会让一次已经算完的运行在写元数据时崩掉 —— 六分钟的活白干，CSV 也没了。

**推荐改法：把解码那一步已经解析出来的结果（路径 + 来源 + 版本）传下来。**
帧就是那个 ffmpeg 解的，传下来才是**同一份事实**；在这里重新解析一次，本身就是第二次派生
（解析器是幂等的，但环境可以在两次调用之间变，而 run.json 声称描述的是**已经解完的那批帧**）。
退而求其次：捕获异常、`decoder` 写 `null` + stderr 一行原因（照 `_get_ffmpeg_version` 的先例）。

### H11 守卫 7 把整个 `video.py` 按文件名豁免了，接近空转

```python
if py_file.name == "video.py":
    continue
```

「只有一个解析器」这条规矩**最容易被破坏的地方正是 `video.py`**（有人再加一个 `_require`），
而你把整个文件豁免了。另外它只认 `subprocess.<attr>([...])` 这一种形状 ——
本仓实际的执行入口是 `video._run(cmd)`，通过 `_run` 传进去的字面量它一概看不见。

改：豁免范围缩到**函数级**（只豁免 `_resolve_ffmpeg_tool` 这一个函数体），
检查面从 `subprocess.*` 扩到本模块的执行入口（`_run` 及类似）。

### H12 `.iss` 的 `vendor\ffmpeg\` 与 `fetch_ffmpeg.py` 的落地目录**不是同一个目录**

- `fetch_ffmpeg.py` 的 `VENDOR_DIR = <仓根>/vendor/ffmpeg`；
- 工作流里 `iscc` 的 `working-directory: packaging`，而 Inno Setup 的相对 `Source:`
  是相对**脚本所在目录**（`SourceDir` 默认值）解析的 ⇒ `.iss` 里的 `vendor\ffmpeg\...`
  指的是 `packaging\vendor\ffmpeg\...`，**东西不在那儿。**

（`dist\...` 那两行是对的：PyInstaller 在 `packaging/` 下跑，`dist` 就在 `packaging/dist`。）
改法二选一：`.iss` 里写 `..\vendor\ffmpeg\*`，或加 `SourceDir=..` 并把 `dist` 路径一起改。
**选哪个都要在真构建里验证过再交。**
